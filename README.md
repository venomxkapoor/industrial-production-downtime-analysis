# Production Scheduling & Workload Analysis — Python and Excel

A small, transparent analysis that compares two simple order-sequencing rules —
**First In, First Out (FIFO)** and **Earliest Due Date (EDD)** — on two work centres,
and measures delivery performance and capacity pressure.

> **Simulated data.** All 80 production orders are fictional. They are generated by
> `src/generate_data.py` with a fixed random seed (42). They are **not** real factory records.
> This is a personal educational portfolio project, not an industrial optimisation system.

## 1. Objective and business context

A fictional small manufacturer has a list of open customer orders. Each order has a processing
time and a delivery due time and is assigned to one of two work centres. Management wants to know:

1. How much work is assigned to each work centre?
2. Which work centre is under greater capacity pressure?
3. How many orders finish late, and how late?
4. How long do orders wait before processing starts?
5. Which of two simple rules performs better — and on which metric?
6. What trade-offs and limitations should be understood?

## 2. Dataset (`data/production_orders.csv`)

| Column | Meaning |
|---|---|
| `order_id` | Unique order identifier (`ORD-001` … `ORD-080`) |
| `original_sequence` | Order in which the orders were received (1 = first) |
| `work_centre` | Assigned work centre: `WC1` or `WC2` (about 60 % / 40 % split) |
| `product_category` | Bracket, Housing, Shaft or Panel (descriptive only) |
| `processing_time_h` | Processing time in hours: 1.0 – 8.0 h in 0.5 h steps (uniform) |
| `due_time_h` | Due time in whole hours after the start of the planning period: 8 – 160 h (uniform) |
| `release_time_h` | Time the order becomes available — 0 for every order |

Input checks (run before every analysis): required columns present, no missing values, no
duplicate order IDs or sequence numbers, processing times > 0, no negative due or release times.

## 3. Assumptions

- All orders are available at planning time 0; both work centres start at time 0.
- Each order is processed entirely on its assigned work centre (no transfers, no multi-step routing).
- A work centre processes one order at a time; orders are never interrupted (no preemption).
- The two work centres operate in parallel and independently.
- Processing times are deterministic. No setup times, breakdowns, operator shortages or shift breaks.
- Time is measured in **continuous processing hours**. This is a modelling simplification and does
  not claim that a real factory runs without breaks.
- **Capacity budget:** 160 h per work centre for the planning period
  (illustrative: 10 working days × 2 shifts × 8 h).

## 4. Scheduling rules

- **FIFO** — within each work centre, orders are processed in their original sequence.
- **EDD** — within each work centre, orders are processed by earliest due time.
  Ties are broken by the original sequence (smaller first), so the result is deterministic.

Both rules use exactly the same orders, assignments and assumptions.

## 5. Metrics

Per order (release time *r* = 0):

| Metric | Formula |
|---|---|
| Completion time *C* | start time + processing time |
| Waiting time | start time − *r* |
| Flow time | *C* − *r* (equals completion time here) |
| Lateness *L* | *C* − due time (negative = early) |
| Tardiness *T* | max(0, *L*) |
| Late order | *T* > 0 (finishing exactly at the due time is on time) |

Per rule: number and % of late orders, average waiting time, average flow time, average and
total tardiness, maximum lateness, total processing time and makespan (latest completion time).

Per work centre: **capacity-pressure ratio = assigned processing hours ÷ capacity budget**.
This is a *planning load ratio*, not measured machine utilisation.

## 6. Results (from `outputs/kpi_comparison.csv`)

| Metric (all 80 orders) | FIFO | EDD |
|---|---:|---:|
| Late orders | 39 (48.8 %) | 41 (51.2 %) |
| Average waiting time | 91.61 h | 88.39 h |
| Average flow time | 95.69 h | 92.48 h |
| Average tardiness | 27.94 h | 13.42 h |
| Total tardiness | 2235.0 h | 1073.5 h |
| Maximum lateness | 153 h | 46 h |
| Total processing time | 326.5 h | 326.5 h |
| Makespan | 206 h | 206 h |

Work-centre load (`outputs/work_centre_load.csv`):

| Work centre | Orders | Assigned | Budget | Pressure ratio | Overload | Late (FIFO / EDD) |
|---|---:|---:|---:|---:|---:|---:|
| WC1 | 49 | 206.0 h | 160 h | 1.29 | 46.0 h | 31 / 41 |
| WC2 | 31 | 120.5 h | 160 h | 0.75 | 0 h | 8 / 0 |

**Interpretation**

- **Trade-off, not a universal winner.** EDD produced slightly *more* late orders (41 vs 39) but
  roughly halved average tardiness and reduced maximum lateness from 153 h to 46 h.
  If the objective is the *number* of late orders, FIFO was marginally better on this dataset;
  if the objective is to limit *how late* orders become, EDD was clearly better.
- **Makespan and total work are identical** (206 h, 326.5 h). Re-ordering jobs without setup or
  idle time cannot change the amount of work or when the last job finishes.
- **WC1 is the capacity-pressure point in this model** (206 h assigned vs 160 h budget, ratio 1.29).
  Under EDD, WC2 has no late orders while 41 of WC1's 49 orders are late. Re-sequencing cannot
  remove an overload; that would require extra capacity, re-assignment or different due dates.
  Because the model has only one stage, this does not prove a bottleneck in a real production system.

Charts are in `outputs/charts/`, a two-page summary is in `reports/production_planning_report.pdf`.

## 7. Repository structure

```
production-scheduling-analysis/
├── data/production_orders.csv        simulated input orders
├── src/generate_data.py              creates the dataset (seed 42)
├── src/analyse_schedules.py          FIFO/EDD schedules, KPIs, charts, Excel workbook
├── src/build_report.py               two-page PDF report from the saved outputs
├── outputs/                          schedules, KPI tables, workbook, charts
├── reports/production_planning_report.pdf
└── tests/test_scheduling.py          automated checks (pytest)
```

The Excel workbook `outputs/production_analysis.xlsx` contains the original orders, both schedules,
KPI tables, work-centre load and the assumptions. All of these are **values calculated by Python**.
The sheet **Worked Example** uses **live Excel formulas** on a 5-order example that can be checked by
hand, next to the Python result for the same example.

## 8. How to run

Requires Python 3.10+.

```bash
# 1. (optional) create and activate a virtual environment
python -m venv .venv
.venv\Scripts\activate            # Windows
# source .venv/bin/activate       # macOS / Linux

# 2. install dependencies
pip install -r requirements.txt

# 3. reproduce the analysis (run from the project folder)
python src/generate_data.py
python src/analyse_schedules.py
python src/build_report.py

# 4. run the tests
python -m pytest
```

The tests (31 checks) cover reproducibility of the data, a hand-calculated 5-order example,
no overlapping jobs, correct formulas, FIFO/EDD ordering and tie-breaking, unchanged total work
and makespan, and agreement between the CSV files, the Excel workbook and the PDF findings.

## 9. Limitations and possible improvements

- Simulated, random data: the results show how the two rules behave on one dataset, not how a real
  plant performs. Real order data would be needed for business conclusions.
- Single-stage model with fixed work-centre assignment; no setups, breakdowns, shift calendars,
  dynamic order arrivals or customer priorities.
- Only one dataset and two rules; no statistical comparison across many scenarios.

Possible next steps: run the comparison over many random seeds, add release times or shift
calendars, add a third simple rule such as Shortest Processing Time (SPT), or test re-assigning
orders from WC1 to WC2.
